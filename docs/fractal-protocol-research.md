# Fractal preset index: protocol research and architecture

Research status: 2026-10-01, including read-only FM9 hardware sessions through `MIDI Forwarder`. This is a design and evidence inventory. The optional [`PresetMaestro.FractalIndex`](../PresetMaestro.FractalIndex/README.md) module now includes the decoder/reader, scan checkpoints and shared JSON cache; the app registers local search and preset/scene tagging. See [the usage guide](fractal-index-usage.md). Saved device presets are read on an explicit user action. Ordinary search never needs MIDI. The historical observations below retain their original scope; synthetic workflow tests do not expand the hardware evidence.

## 1. Existing PresetMaestro architecture

PresetMaestro is a Windows .NET 10 Avalonia desktop application. `PresetMaestro/Program.cs` starts `App`, which creates `MainWindow`. `MainWindow` is a code-behind class split across partial files; layout and events are built in C# with some AXAML. There is no general-purpose dependency-injection container. Dependencies are passed through the `MainWindow` constructor for tests, while the normal constructor creates `MidiManager`, `ProfileStore`, and `PresetNameClient`.

At the start of this research, the solution (`PresetMaestro.slnx`) had the application, `PresetNameSync.Core`, a separate name-sync probe, and xUnit application/probe tests. The obsolete probe and temporary research harnesses were removed on 2026-10-03, with its protocol tests moved into `PresetMaestro.Tests`. `Directory.Build.props` treats warnings as errors. The application targets `net10.0-windows10.0.19041.0`, publishes a self-contained Windows single file, and references Avalonia 11.2.3 and NAudio 3.0.1. The shared name decoder targets `net10.0`. There was no SQLite database or general preset-search index at that point. Profile settings and Favorites use JSON files under `%APPDATA%\PresetMaestro` (`ProfileStore`, `SettingsManager`, `FavoritesManager`). Existing cached preset names are slot-keyed; scene names are keyed by MIDI port pair and slot (`AppSettings`, `SceneCacheEntry`). Neither cache is a safe logical-preset identity store.

Existing Fractal/device code is useful but deliberately narrow:

| Code | Current responsibility | Reuse boundary |
|---|---|---|
| `PresetMaestro/Midi/MidiManager.cs`, `IMidiManager.cs` | One open MIDI input/output pair, SysEx send/receive, PC/CC, thru | Reuse connected ports and serialized request access; never open a competing handle inside the feature. |
| `PresetMaestro/Midi/PresetNameClient.cs` | Queued name, current-state and saved-scene-name reads; timeout/cancellation quarantine | Reuse or extend its transaction coordination, not its name-only result as a preset parser. |
| `PresetNameSync.Core/SysexProtocol.cs`, `SysexAssembler.cs` | FM9 name/current-state framing and fragmented SysEx assembly | Reuse framing/assembly after model-specific verification. Its fixed `0x12` model byte and 0–511 address limits cannot simply serve Axe-Fx III. |
| `PresetNameSync.Core/StoredPresetDecoder.cs` | Saved FM9 `0x03` dump, integrity/decompression, preset and eight scene names | Valuable decoder seed; it does **not** decode Amp block channels, model IDs, scene channel/bypass or Scene Ignore. Keep the existing name path stable. |
| `PresetMaestro/Midi/FractalDeviceInformationClient.cs` | Captured FM9-Edit discovery, FM9 name read, model classification | Reuse validated identity behavior; current enum collapses all Axe-Fx III hardware revisions and does not identify firmware. |
| `PresetMaestro/Core/DevicePresets.cs` | Existing picker limits (`FM9=512`, `AxeFxIII=1024`) | Do not reuse as index capability truth: original Axe-Fx III has 512. Preserve its current UI behavior until a separately reviewed change. |
| `MainWindow.Favorites.cs`, `Core/Favorite.cs` | Existing Add Favorite card, validation, tags, save | Future action should navigate to Favorites and call `ShowFavoriteEditor(new Favorite {...}, isNew: true)`, prepopulating display-adjusted preset/scene through a narrow host method. Do not add a new Favorites store or wire it in this phase. |
| `MainWindow.FavoriteSearch.cs` | Search *Favorites* by name, tag, displayed numbers and cached names | Separate concern; the proposed index gets its own cached preset/scene search. |

The `Favorite` stores a displayed preset number and scene 1–8, so the future adapter must convert the index's zero-based device slot using the active profile's display offset and verify the connected/profile device before offering the action. A favorite remains a normal existing favorite; its `Id` identifies the favorite, not the underlying Fractal preset. For a profile associated with multiple physical units, the current Favorite format cannot say which unit its number targets. Do not enable the index-to-Favorite shortcut for that case until per-device Favorite applicability is designed. The narrow UI integration point is `MainWindow.Favorites.cs:ShowFavoriteEditor` plus page navigation. Nothing should mutate `Favorite` or `FavoritesManager` during the research or first probe.

## 2. Evidence convention and primary sources

- **OFFICIAL:** Fractal product/manual or published third-party MIDI guide.
- **OPEN IMPLEMENTATION:** inspectable third-party code/docs, whose hardware and firmware coverage must be checked.
- **OBSERVED:** captured device traffic or hardware behavior recorded in this repository. A synthetic unit test alone is not observation.
- **INFERRED:** an engineering conclusion derived from the above, awaiting direct validation.
- **UNKNOWN:** no reliable evidence, or insufficient evidence for the target variant/firmware.

The [Axe-Fx III MIDI for Third-Party Devices, rev. 1.4](https://fractalaudio.com/downloads/misc/Axe-Fx%20III%20MIDI%20for%203rd%20Party%20Devices.pdf) is an **OFFICIAL** live-control/status guide for Axe-Fx III firmware 1.13+. It documents model byte `0x10`, XOR-checked SysEx, current effect bypass/channel, scene, name, and status queries. It does **not** document saved-preset dump requests, full Amp parameters, firmware discovery, preset CRC, or persistent preset identity. Its live status dump describes the *currently loaded* preset; it cannot answer which Amp models exist in inactive saved channels or all scenes.

**Physical-unit identity review (2026-10-02):** Rechecked that published guide for a serial-number or unique-unit query; none is specified. The validated `FractalDeviceInformationClient` WHO_AM_I exchange accepts a ten-byte response containing the model and fixed success/status fields, not a serial number. Its separate FM9 name read returns the editable device name. Neither provides verified persistent identity for an individual physical unit. This does not establish that no private/editor protocol can expose such an ID; that remains unknown. The local library GUID is generated by Preset Maestro and is not a hardware identifier. Continue using explicit profile-to-library assignment and the existing pre-sync physical-unit confirmation, including when accessing the FM9 through MIDI Forwarder. This review used documentation and existing captures/code, with no new hardware requests.

**OBSERVED FM9 session (2026-09-30):** Windows listed `MIDI Forwarder` as one MIDI input and output. Temporary read-only console harnesses used the existing `PresetNameSyncProbe/Midi/MidiProbeClient.cs` and `PresetNameSync.Core` without changing production code. The `0x0D` slot-0 name query returned a name. `0x03` saved reads of slots 0 and 43 each returned one `0x77` header, eight `0x78` data frames and one `0x79` footer; `StoredPresetDecoder` accepted their checksums/CRC and decoded both preset names and eight scene names each. Current-preset/name/scene queries before and after reported the same active slot (43) and the same eight live scene names. This confirms two saved reads on **this attached FM9**, with no observed active-preset change. Firmware, audio continuity, unsaved edit-buffer preservation, Scene Ignore fields, and other devices were not verified. No raw user preset dump was retained in the repository.

**OBSERVED repeat/boundary session (2026-10-01):** A disposable console harness under ignored `build_test/fm9-readonly-validation/` opened both `MIDI Forwarder` ports and received a valid FM9 identity reply. It queried current slot/scene, then read saved slots **122, 0, 43, 256 and 511** with the existing `StoredPresetDecoder`; all five completed checksum/CRC and decompression checks and yielded eight scene-name fields. Slots 256 and 511 had no nonblank scene names; this alone does not prove they are empty. ## 3. Device findings and compatibility matrix

The FM9 has 512 preset locations, eight scenes, two Amp blocks, and four channels per Amp block (**OFFICIAL**, FM9 manual). The Axe-Fx III original has 512 preset locations; Mark II and Mark II Turbo have 1024 (**OFFICIAL**, Axe-Fx III manual). The [official block inventory](https://www.fractalaudio.com/axe-fx-iii/) lists two Amp blocks and four channels. Turbo's higher processor speed does not establish a distinct stored-preset protocol (**UNKNOWN**). Capacity and revision must be resolved into a `DeviceCapabilities` record per connected unit, not a switch on the current three-value `DeviceModel` enum.

**FM9 protocol detail.** The repository observed FM9-Edit's broadcast `WHO_AM_I` (`F0 00 01 74 7F 00 7A F7`), an FM9 `0x12` reply, and an FM9 device-name request/reply (`FRACTAL-DEVICE-INFORMATION.md`). A previous guessed `0x46` request returned an error on firmware 12.0: strong evidence against inventing transactions. The name client uses the `0x0D` and `0x0E` queries, while `StoredPresetDecoder` recognizes `0x77` header, `0x78` chunks, `0x79` footer, a 16,384-byte saved image, CRC and a compressed body. The saved-dump request is `0x03`; the 2026-09-30 and 2026-10-01 FM9 reads confirm this decoder path on attached hardware through slot 511, but do not assume identical envelopes on Axe-Fx III. Existing 512-slot checks and `0x12` frames make cross-device reuse unsafe without an explicit device strategy. No active-preset change was observed during these saved reads; the user heard no audio change during one monitored transfer. Preservation of pre-existing unsaved edits during a saved read remains untested.

**Axe-Fx III protocol detail.** The official guide permits `0x0A` live bypass, `0x0B` live channel, `0x0C` scene, `0x0D` patch name by number, `0x0E` current scene name, and `0x13` current-effect status. Queries must use their documented `0x7F` values; setting a normal value would change live state. `0x0D` is suitable for a read-only slot-name sweep but does not prove a slot is empty, deliver its stored Amp model/channel content, or identify a logical preset. `0x0E` addresses a scene in the current preset, so sweeping all stored scene names requires either a separately validated saved-dump parser or disruptive preset selection. The open gen-3 parsers suggest related saved formats across Axe-Fx III/FM9, but exact request, response, model roster, upper-slot addressing, and firmware variation remain unverified per target. The current application only enables full name reads for FM9 and deliberately disables them for Axe-Fx III (`README.md`, `PresetNameSync.Core/README.md`).

**Transport and operation.** USB and 5-pin MIDI are available (**OFFICIAL** manuals). Existing `SCENE-NAMES.md` estimates roughly 12.6 MB for 512 FM9 saved preset dumps over DIN and over an hour in a bulk scan; 1024 would approximately double bytes if format/size match (**INFERRED**). Do not promise speed or a universal fixed delay. Use a single request at a time, bounded frame/total lengths, checksum verification, response correlation, timeout/backoff and cancellation. Preserve completed slots and store per-slot errors; quarantine late replies because the current SysEx protocol lacks transaction IDs (`PresetNameClient`, `SCENE-NAMES.md`). Yield to foreground controller operations; pause or cancel sync if the user changes preset. Detect port loss and refuse to start while a known editor owns the port. Concurrent FM9-Edit/Axe-Edit behavior and exact Windows MIDI port exclusivity are environment-dependent (**UNKNOWN**); test rather than assume safe coexistence. The current app already warns users about busy ports. Respect read-only operation and verify that stored reads neither switch the active preset nor interrupt audio on all target devices (**UNKNOWN** outside the code's design intent).

### FM3 integration added 2026-10-01

The [official family comparison](https://www.fractalaudio.com/family/) and [FM3 owner's manual](https://www.fractalaudio.com/downloads/manuals/FM3/FM3-Owners-Manual.pdf) describe 512 preset slots, a 12-column × 4-row grid, one Amp block with four channels, and eight scenes. These are separate device capabilities, not FM9 defaults. The [reviewed open body decoder](https://github.com/TheAndrewStaker/mcp-midi-control/blob/main/packages/fractal-gen3/src/presetBody.ts) identifies model byte `0x11`, 144-word Amp channel records and model IDs at parameter word 0. FM9 uses 147 words and parameter word 4; Axe-Fx III uses 142 words and a header-based model field. The FM3 byte layout is **OPEN IMPLEMENTATION** evidence and remains a hardware candidate.

The optional core now supplies a distinct FM3 definition, validates its single-Amp limit, uses its grid bounds and model offsets, and dispatches index requests only to a matching connected FM3. The FM3 catalog is independently scoped by family and firmware; it starts empty and cannot fall back to observed FM9 names. A synthetic slot-511 dump exercises the application MIDI adapter, envelope integrity checks, body decoding, eight scene states and unknown-ID handling. Additional tests cover device mismatch rejection, catalog isolation, grid relocation and incomplete bodies. No FM3 hardware read, audio check, firmware discovery or populated catalog is claimed. The existing name-only APIs remain on their verified FM9 path.

Grid position has no product meaning for this index. Only Amp instance presence is read from the grid to check the decoded records; no coordinates or cables are retained. A block can move without changing its indexed model or scene values. Instance numbering is preserved even when a preset contains only Amp 2.

## 4. Preset, scene, and Amp identity

The searchable hierarchy is `Preset → AmpBlock → Channel → FractalAmpModel` and `Preset → Scene → saved AmpBlock state → selected Channel → AmpModel`. A preset does not have one direct Amp model. The index needs three distinct predicates:

| Predicate | Meaning | Required evidence |
|---|---|---|
| `CONTAINS` | Any saved Amp block channel holds the model | Decoded block and channel, including inactive channels. |
| `SELECTS` | A scene's saved selection points to that channel | Decoded scene/block channel state. May be conditional with Scene Ignore. |
| `USES` | Selected channel and Amp block engaged | Decoded scene channel **and** bypass; this is block-state use, not proof of an audible signal route. |

The manual shows that Scene Ignore is a **per-channel** setting, introduced in FM9 firmware 3.0 and Axe-Fx III firmware 19.05 ([FM9](https://www.fractalaudio.com/downloads/manuals/FM9/FM9-Owners-Manual.pdf), [Axe-Fx III](https://www.fractalaudio.com/downloads/manuals/axe-fx-3/Axe-Fx-III-Owners-Manual.pdf)). Once a channel with Scene Ignore enabled is selected, later scene changes need not alter that block's channel or bypass; manual switching can re-enable scene control by moving to another channel. Thus a scene's *saved programmed* Amp state may be statically decoded, while its *effective live* selection may depend on the preceding scene and manual actions. Represent `Programmed`, `EffectiveKnown`, `Conditional`, and `Unknown` separately. The default search may safely report `CONTAINS`; `SELECTS`/`USES` should carry the programmed/effective qualifier and should not assert an unconditional effective result when Scene Ignore or missing decoder data makes it uncertain. Scene Revert and unsaved edits are additional live-state factors.

No stable device-provided preset UUID or scene UUID has been found in the official guide, manuals, repository decoder, or reviewed open format notes (**UNKNOWN**, not proof of absence). Scene number 1–8 is the only reliably exposed address in the official live query. Treat `device + preset slot + scene index` as physical addressing, not durable scene identity. Renaming a scene leaves its index but changes content; replacing/copying a scene can leave index/name while changing settings. Meaningful scene movement semantics should be tested in FM9-Edit/Axe-Edit; do not infer a move from matching names. Store scene lineage only as an optional, evidence-backed local association. Do not silently transfer scene tags or annotations in an ambiguous replacement.

For presets, keep three identities distinct:

1. **Physical:** verified device instance + slot. A port name alone is insufficient: two devices can share names, as `SCENE-NAMES.md` notes. Record model/revision, validated serial or stable hardware ID if obtainable, otherwise a user-confirmed device identity with uncertainty.
2. **Content:** SHA-256 of exact saved bytes and a versioned normalized fingerprint excluding address and optionally names after the byte layout is proven. A CRC in the stored image checks integrity and can help detect byte changes *after retrieval*; it is not a logical ID or a cheap remote change indicator.
3. **Logical:** a local `TrackedPreset` GUID representing the user's intended preset lineage. It survives confirmed rename/move/edit, may branch on copy, and can become unresolved.

No content hash by itself proves whether a user moved a preset, copied it, restored a backup, or recreated it. Matching a slot or similar name alone is never sufficient to transfer tags.

## 5. Real amplifier normalization

Keep raw Fractal model ID **and** raw display name, qualified by device family, firmware and roster version. The integer's stability across firmware or devices is **UNKNOWN**; never join to a real amp using an unqualified ID. Seed a curated `FractalAmpModel` ↔ `RealAmp` mapping with `manufacturer`, `family`, `specific model`, `channel/input/variant`, aliases, attribution URL, confidence (`verified`, `probable`, `ambiguous`, `Fractal-original`, `unmapped`) and firmware applicability. Make the relationship many-to-one or many-to-many: several Fractal variants can model one amplifier, and some Fractal originals have no real amplifier. Preserve conflicting candidates for review rather than fabricating certainty.

The firmware-12.00 slot-125 comparison found raw Amp ID `271` at a valid channel position while the reviewed open roster has no `271` entry. FM9-Edit displayed **Matchbox D-30 EF86** for that position. Keep the ID and an `unmapped` status if the shipped roster lacks it; promote this observed `(FM9, firmware 12.00, 271)` name only in a separately reviewed catalog update with its screenshot provenance. A missing roster row must not suppress the channel or its preset/scene search result.

For example, `Brit 800 → Marshall → JCM800 → 2204` is supported historically by [Fractal's Axe-Fx II manual](https://www.fractalaudio.com/downloads/manuals/axe-fx-2/archive/Axe-Fx_II_Owners_Manual_-_1002.pdf), but carry model-generation provenance and verify the current FM9/Axe-Fx III roster before marking the mapping confirmed. The [Fractal Wiki amp-model catalog](https://wiki.fractalaudio.com/wiki/index.php?title=Amp_models) is a useful community reference, not an official stable ID table. Do not copy a large third-party database without checking license and attribution. Search both raw names and normalized manufacturer/family/model/variant/aliases; show the raw name and mapping status to users. Reindex when the mapping catalog changes without needing to resync the device.

## 6. Incremental sync and tag reconciliation

There is currently no verified inexpensive per-slot remote hash, CRC, revision or modified timestamp query for FM9 or Axe-Fx III (**UNKNOWN**). The official `0x0D` name query is cheap but a name match does not establish unchanged content. A full stored dump has a CRC and supports exact/normalized local hashes after transfer (**OPEN IMPLEMENTATION**); it cannot avoid the transfer. Proposed safe modes:

1. First run: identify unit/capabilities/firmware, enumerate supported slots, retrieve saved snapshots one by one, decode and commit each atomically, then mark complete only after all slots are checked. Never erase a good prior snapshot after one corrupt/timeout response.
2. Subsequent verified mode: if a firmware-specific cheap remote change indicator is validated, compare it and fetch changed slots. Store indicator kind, scope, firmware and validation status. Names can prioritize slots but cannot prove unchanged content.
3. Until then: explicit full scan or user-selected slot ranges, with optional name sweep and a conspicuous **partial/stale** cache status. If a name is unchanged and the user elects a fast sweep, leave previous Amp data marked unverified rather than describing it as current.
4. Any firmware/model capability change invalidates the relevant decoder/indicator assumptions. Retain old snapshots for audit; rescan rather than silently reinterpret.

Use a per-device `SyncState` with started/completed times, firmware, decoder version, last successful slot and slot-specific outcome. Resume by retrying unfinished/failed slots without assuming the device is unchanged since interruption; for consistency, resweep metadata or begin a new scan generation. Searches read committed local snapshots only and display age and completeness.

Reconciliation should compare old and new slot occupancy, exact bytes, versioned normalized fingerprint, names, and Amp/scene structure across the *entire device scan*. Preserve tags on an unchanged snapshot. A unique, byte-identical preset at a new slot is a **candidate move**, but a copy leaves two identical candidates; require explicit user resolution before moving a logical identity when both remain or when competing candidates exist. A same-slot rename/edit can be an association candidate if there is strong continuity and no competing matches; keep the old tags pending if overwritten content is plausible. Backup restore may reintroduce an old fingerprint; offer relink rather than auto-reassign. Modified presets and editor saves may alter bytes extensively, so allow a user-confirmed relink. An overwritten slot creates an unassigned new `TrackedPreset`; tags on the displaced one stay in history. Never infer lineage from slot number or similar name alone. Ambiguity is a first-class state (`confirmed`, `candidate`, `ambiguous`, `orphaned`), with candidate reasons and an explicit resolution action. Copies should start a new logical identity unless the user chooses to duplicate tags. Rename/move/restore/replace of scenes follows the same caution for scene tags.

Preset and scene tags are PresetMaestro-local metadata, separate assignments from existing Favorites tags and never written to the Fractal device. With many-to-many profiles/devices, they belong to a **profile + device + tracked preset** or **profile + device + tracked preset + tracked scene** relationship, not a slot. The same device scan is shared across profiles while each profile may tag it differently. See [the UX research](fractal-index-ux-research.md) and [the data design](fractal-index-data-design.md) for interaction, storage and lifecycle rules.

## 7. Local model and storage

Use a feature-owned SQLite snapshot/query cache under `%APPDATA%\PresetMaestro\FractalIndex\` (one schema/version per feature, distinct from profile JSON). A single local database is adequate for 1024 presets, 8192 scenes, up to 8192 Amp-channel positions and 16384 scene/Amp-block positions; correctness matters more than tuning. Do not add Amp fields to `AppSettings` or Favorite JSON. Store user-authored tags and profile/device associations in a portable profile JSON sidecar; the database may keep a rebuildable projection for joins/search. A physical unit's scan is stored once and reused by all associated profiles. Profile rename/copy/delete/import/export must carry the sidecar and any portable decoded snapshots as described in [the data design](fractal-index-data-design.md). Define explicit migrations and cache reset/export so deleting the snapshot cache never deletes tags.

Suggested normalized tables/records:

| Concept | Important fields/relations |
|---|---|
| `Device` / `DeviceCapabilities` | Local ID, reported model/revision/firmware, validated serial if available, identity confidence; preset/scene/Amp/channel maxima, capability provenance. |
| `Profile`, `ProfileDevice` | Stable profile identity and explicit many-to-many device association with verification/confidence; portable source is profile JSON, with an optional database projection. |
| `PresetSlot` | Device ID + zero-based slot, occupancy `present/empty/unknown`, current snapshot reference; physical address only. |
| `PresetSnapshot` | Immutable ID, slot at capture, raw bytes or encrypted-at-rest policy if later desired, exact and normalized hashes, CRC result, decoder version, name, timestamp and completeness. |
| `TrackedPreset` | Local GUID, logical identity state, creation/history; link to zero or more snapshots through explicit lineage/reconciliation records. |
| `Scene` | Snapshot ID + scene index 0–7, raw/decoded name and program state; optional local lineage only when evidence supports it. |
| `Block`, `BlockChannel` | Snapshot/block instance, channel A–D, raw model ID/name, per-channel Scene Ignore if decoded, decode status. |
| `SceneBlockState` | Scene/block, programmed channel and bypass, effective-resolution status and uncertainty reason. |
| `FractalAmpModel`, `RealAmp`, `AmpAlias`, `AmpMapping` | Firmware-qualified raw identity, normalized amplifier identity, aliases, source, confidence, review/version metadata. |
| `PresetTag`, `SceneTag` | Search projection of profile-owned JSON assignments to tracked presets/scenes on a particular device; never sent to device. |
| `SyncRun`, `SyncSlotState`, `IdentityCandidate` | Per-run progress/errors/indicator, resume data, and explicit reconciliation candidates. |

Keep raw byte offsets/unknown fields and decoder confidence in snapshots. A failed or partial decode can still preserve the raw evidence and name without falsely creating channel/scene facts. Index raw/normalized names and projected tags with ordinary SQLite indexes initially; SQLite FTS5 can be added if measured search needs it. All search predicates should carry `snapshotId`, `deviceId`, and certainty so stale or uncertain results are visible. A scene result should expose device/slot/scene and display offset context for a later Favorite action, without referencing Favorites from the feature core.

## 8. Concrete feature isolation and build plan

**Recommended mechanism:** separate feature projects with one opt-in MSBuild property and one narrow application registration seam. Use `EnableFractalIndex=false` by default. Only when true, `PresetMaestro.csproj` includes a `ProjectReference` to `PresetMaestro.Fractal.Avalonia` and compiles a small feature adapter; otherwise compile a no-op adapter. Keep conditional compilation confined to this seam, not across the app. The feature core is independently buildable and testable, and the application still builds/runs with its existing MIDI/name behavior when the property is false. The feature must not initialize its sync service, create the SQLite file, or register MIDI handlers while disabled. At runtime, a setting can hide/disable the feature without opening device handles; the build property is the complete-removal boundary. Resolve publishing of the optional assembly/SQLite dependency in both normal and single-file builds before release.

Concretely, add a conditional `ProjectReference` in `PresetMaestro.csproj` with `Condition="'$(EnableFractalIndex)' == 'true'"`, and add `FRACTAL_INDEX` to `DefineConstants` under that same condition. One always-compiled `OptionalFractalIndex.cs` has the only `#if FRACTAL_INDEX`: its enabled branch creates the feature view/service, and its disabled branch returns without work. `MainWindow` calls that seam once after `BuildLayout()`; the adapter can attach a navigation item through a small host callback. `PresetMaestro.Fractal.Avalonia` references `PresetMaestro.Fractal.Core`, while neither feature project references the main executable. The feature UI defines its own small host interface (serialized read-only SysEx request, device/capability context, navigation insertion and, later, an Add Favorite callback); the application's enabled adapter implements it. Do not create a second MIDI connection or let the feature bypass the current request queue. Verify `dotnet build PresetMaestro/PresetMaestro.csproj -p:EnableFractalIndex=false` and `...=true` plus single-file publish in the implementation phase.

Suggested ownership in the next phase:

| New feature-owned path | Purpose |
|---|---|
| `PresetMaestro.Fractal.Core/` | Capabilities, immutable decoded model, sync/reconciliation/search contracts, decoder interfaces, normalization data and SQLite repository. No Avalonia dependency. |
| `PresetMaestro.Fractal.Avalonia/` | Optional search/sync UI and a narrow host adapter. No separate Favorite implementation. |
| `PresetMaestro.Fractal.Probe/` | Independent console research harness: one-preset read/print, raw capture and transport diagnostics. |
| `PresetMaestro.Fractal.Tests/Fixtures/` | Captured fixtures plus synthetic edge cases; no physical device required for regressions. |
| `PresetMaestro/OptionalFractalIndex.cs` | Sole always-present no-op/conditional registration seam, accepting an existing MIDI request service and host UI callbacks. |

Expected shared changes **after** probe acceptance:

| Existing file | Why it changes |
|---|---|
| `PresetMaestro/PresetMaestro.csproj` | Conditional project reference/compile item behind `EnableFractalIndex`; feature-disabled build remains dependency-free. |
| `PresetMaestro.slnx` | Add independently buildable feature and test/probe projects; solution presence alone does not enable runtime feature. |
| `PresetMaestro/MainWindow.axaml.cs` | One call to optional registration after normal layout is built, with teardown on close; no Fractal parsing. |
| `PresetMaestro/MainWindow.Layout.cs` (or its existing navigation host) | Expose one small optional page/nav insertion point if the current layout cannot accept a feature view directly. Avoid changes to other pages. |
| `PresetMaestro/Midi/IMidiManager.cs` / `MidiManager.cs` **only if required** | Expose a shared read-only, serialized SysEx transaction lease. The feature must not bypass `PresetNameClient`'s queue or open a second port. Prefer an adapter over changes here if the existing surface suffices. |
| `PresetMaestro/Midi/PresetNameClient.cs` **only if required** | Put bulk reads and existing foreground reads under the same queue/cancellation priority. Do not change current name behavior. |
| `PresetMaestro/MainWindow.Favorites.cs` **later only** | A narrow method to open the existing Add Favorite editor with a proposed preset/scene; feature acceptance and identity checks precede wiring. |

The proposed portable tag/association layer adds an optional profile JSON sidecar and stable profile ID, while leaving existing settings/Favorites fields readable and legacy two-file imports accepted. Narrow profile lifecycle callbacks are needed for copy/rename/delete/import/export; manual file replacement/rescan must be handled as an unverified association. Disabling the runtime feature unregisters its page/actions and stops background work. Building with `EnableFractalIndex=false` excludes feature references/UI and all feature MIDI initialization, leaving its inert local database file for possible re-enable. Complete removal means delete the feature projects, their tests/probe, and the one `OptionalFractalIndex` call/seam plus conditional csproj/solution entries; the existing app's Favorites, name cache and MIDI controller remain. This is a proposed file plan, not an instruction to perform those edits during research.

## 9. Dependencies and MIDI library

Keep NAudio for the first Windows prototype because the application already uses it (`NAudio.Midi` input/`NAudio.WinMM` output), with a verified large-SysEx receive buffer and existing fragmented-frame assembler. A new library would create an additional port owner and cross-library timing differences without solving the undocumented preset format. The feature core should take a small transport interface so a later cross-platform backend is possible. The only likely new production dependency is `Microsoft.Data.Sqlite` in the feature core; version, native packaging and single-file publication must be checked when implementing. A separate database helper/ORM is unnecessary at this scale.

## 10. Firmware and unresolved protocol questions

Priority questions for recorded fixtures and a physical device on each target:

1. Which read-only exchange reports exact firmware, hardware revision and a stable device identifier? Can Mark II/Turbo be distinguished without user input? Is the original's 512-slot capacity discoverable?
2. Does a read by saved slot work on each model and firmware, including slots 512–1023? Is it read-only, and does it leave active preset, audio and unsaved edit buffer unchanged?
3. Do full transfers contain both Amp instances, all four channel model IDs and every scene's selected channel/bypass? What are the verified offsets and model-roster lookup/version rules? Is Scene Ignore stored per channel and how is it encoded?
4. Does a preset or scene contain a durable identifier, or only number/name/content? How do rename, move, copy, overwrite, backup restore and editor operations alter exact and normalized fingerprints?
5. What denotes an empty slot? Can name queries distinguish empty from a named blank/default preset? Is there a cheap per-slot revision/hash/CRC/metadata query that avoids full dumps?
6. Are FM9 and Axe-Fx III dump envelopes, address ordering, chunk count, image size, compression and CRC identical on actual target firmware? What errors and negative acknowledgments are returned?
7. What rate and timeout work over USB and DIN? How do Windows ports behave alongside FM9-Edit/Axe-Edit and on disconnect/reconnect? How is a partial transfer recovered?
8. How should the parser interpret global blocks, modifiers, Scene Revert and unsaved live edits if the product eventually promises more than saved programmed Amp state?

Firmware can add/reorder models or modify the preset body while preserving a familiar SysEx envelope. Decoder support should be an explicit `(device family, firmware range, format version)` capability. Unknown versions may still retain raw/name data but must not produce confident Amp/scene claims. Treat the open parser as a candidate, add golden fixtures from each target, and compare against the device/editor screen on the same saved preset.

## 11. Feasibility gates before implementation, then phases

**Research gate, not feature building.** The attached FM9 passed the central feasibility question on the editor-reported firmware **12.00**: saved reads contain Amp-channel model IDs and all programmed scene channel/bypass entries; a varied two-Amp preset's eight channel-model positions and scene channel sequence matched FM9-Edit; scene-1 engaged and bypassed examples matched independent live status. The user heard no audio change during one monitored saved read. This warrants an FM9-specific design path, not a multi-device production commitment or a claim that a complete scan is inaudible. Before implementing, resolve the remaining FM9 risks around Scene Ignore, unsupported model IDs, firmware-qualified decoding, and approved byte-exact fixtures. Capture raw fixtures only with the device owner's consent and keep personal presets out of the repository by default.

The Axe-Fx III Original and Mark II/Turbo remain **NO-GO for a support claim until target-device validation**. The open implementation is promising but does not prove read-by-slot on those units, upper-half addressing, revision discrimination, or firmware compatibility. Obtain hardware or trustworthy byte-exact captures from each variant before enabling it. If saved reads or field decoding fail on a target, reconsider that target's design before adding a production sync/index path for it. Do not use the FM9 success as evidence that the Axe-Fx III variants already work.

1. **Finish research validation:** independent console probe only. On each target, connect, identify model/revision, read firmware through a captured transaction, read one saved preset, decode both Amp blocks/channels A–D and eight scene channel/bypass states, compare to the editor/front panel and read-only live status without changing performance state. Test an empty slot, a two-Amp preset, Scene Ignore, and upper slot 1023 on Mark II/Turbo. Record each result as pass/fail/unknown. On the FM9, the varied two-Amp model/channel comparison and one monitored read have passed; read-only MIDI firmware retrieval, Scene Ignore, true empty-slot semantics and other firmware versions remain open.
2. **Decoder fixtures:** after hardware validation, preserve approved byte-exact FM9 and Axe-Fx III captures. Test one/two Amp blocks, four different models, multiple scene assignments, bypass, names, Scene Ignore, empty slot, corrupt/truncated frames and firmware variants. Use synthetic fixtures for edge cases but label them synthetic. The current repo's synthetic `StoredSceneTests` is a starting pattern, not proof of hardware behavior.
3. **Index core:** only after the relevant target gate passes, add capability profiles, immutable snapshots, SQLite migrations, mapping catalog, `CONTAINS`/qualified `SELECTS`/`USES` query semantics, and explicit sync/resume. Unit tests use raw fixtures with no MIDI hardware.
4. **Identity/tags:** add reconciliation candidates and user-confirmed relink/copy decisions. Test rename, move, copy, edit, overwrite and backup restore with fixtures; never silently rehome tags.
5. **Optional UI:** add explicit Sync and cached search through the one registration seam; only then offer the reviewed Add Favorite adapter. Verify feature-off and feature-on builds, and disabled startup with no feature MIDI/database activity.

**Recommended first production coding milestone after the research gate:** a feature-core decoder plus fixture tests for the validated device/firmware. The disposable console feasibility experiment is research, not that milestone. Full-device synchronization and UI follow only after decoding and identity semantics are supported by fixtures.
