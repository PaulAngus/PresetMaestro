## MIDI connection and library verification (2026-10-07)

The MIDI identity exchange supplies a reported model and name before the library comparison begins. Those reported facts are retained for routing and settings, while the connection card, application header and Preset Sender now distinguish the transport connection from the check of the current profile's saved library. Before a check, or after a cancelled/incomplete/unavailable check, the card and sender say **MIDI connected · Device not checked** and the header says **Device not checked**, with a neutral indicator. During a comparison or library sync they say **Checking device…**, with the existing activity color. A matching comparison or completed baseline sync shows the reported model/name in the theme's readable success foreground. A completed comparison needing review shows the model/name with **Library needs review** and an attention color; the header keeps that status concise. A new connection, profile or assigned library derives a fresh unchecked state from the same context used by the sync dialog. Starting a new sync also removes the previous confirmation until its result is available.

[Fluent 2 badge guidance](https://fluent2.microsoft.design/components/web/react/core/badge/usage) recommends short descriptive states near the relevant content and deliberate use of semantic colors. [Windows InfoBar guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/infobar) describes matching severity to the message and accompanying color with text. These principles are applied to the existing Avalonia status labels and header indicator; no extra InfoBar or task action is introduced. The wording, delayed device-name display and shared presentation across these surfaces are product choices responding to the user's screenshot, not Microsoft requirements. The application's existing success and attention foreground tokens supply readable theme colors; a dark-theme activity indicator remains distinct from a successful check. No deliberate deviation from the cited status guidance.

The connection card and sender text wrap within their existing layout. The short header keeps its current width and exposes the complete status in its tooltip and accessible name. The full displayed status is also the accessible name of each body label, and the connection card announces changes politely. Status updates leave keyboard focus on the user's current control; existing connection, sync and dismissal actions retain their behavior.

Validation: 54 focused connection, navigation, library-check and first-sync cases passed. The complete Release suite passed 702 tests, with five opt-in hardware checks skipped. These checks cover the initial unchecked state, both comparison stages, cancellation, failed/incomplete reads, completed matches and mismatches, missing firmware, reconnecting, name reads and preserved MIDI routing. Status text, accessible names and header tooltips agree across the mounted surfaces, and success styling is withheld until the current library is confirmed. The build with Preset Index disabled also passes. Skia renders of Config were inspected in both themes at 1000×640 and 1440×850 for unchecked, running and review states; Preset Sender was inspected at 1000×850 and 1440×850, alongside completed-check headers. Labels remain readable without obscuring connection actions or navigation.

The connection card's “Hardware and routing” subtitle was removed on 2026-10-07 at the user's request; the MIDI Connection heading already identifies the section. The existing title-to-content spacing closes up naturally. Light and dark Config renders were inspected at 1000×850 and 1440×850, and five existing Config and keyboard/profile checks passed.

## Profile import and shared libraries

Reviewed 2026-10-06. Import previously assigned fresh library IDs unconditionally, even for an export of a library already saved on this computer. Duplicate names were distinguished with GUID fragments, which gave users no useful basis for choosing. Import now retains source identity while reading the export and asks which saved library to use in the existing name/import dialog.

[Fluent 2 dropdown guidance](https://fluent2.microsoft.design/components/web/react/core/dropdown/usage) calls for a visible label, descriptive option text and an explicit default selection. [Windows combo-box guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/combo-box) recommends single-line options, logical ordering and the most common choice first. [Fluent 2 dialog guidance](https://fluent2.microsoft.design/components/web/react/core/dialog/usage) recommends focused forms, specific action labels, Escape dismissal and returning focus to the invoking control. These documented recommendations are applied with the existing Avalonia Fluent controls and theme. The library choice sits within the existing import dialog, with separate Import/Overwrite and Cancel controls, rather than adding another modal step. Long labels have ellipsis, full-text tooltips and accessible text.

Product choices: importing for the connected device is the common path. When its model is compatible and the currently assigned library is saved, that library is recommended. Without it, a library with the export's original identity is recommended if still saved locally. Matching names, models or preset contents alone never silently merge libraries. Users can choose any saved library of the same exact variant, or keep a separate imported copy for offline use. A reference-only export instead offers choosing a library later and explains that no saved presets were included.

Reusing a saved library preserves its current presets, scenes, amps and MIDI mapping; imported annotations and review history refer to the chosen library but stay within the new profile. The export's older snapshot is omitted for reused libraries so it cannot overwrite or later resurrect stale local data. Separate snapshots retain their contents with independent IDs. Colliding names include “imported for” and the chosen profile name; repeated copies get a numeric suffix. Existing duplicates show model and the profiles using them, or “Imported copy”/“Unassigned copy”, instead of opaque IDs. Config explains what a library holds and how profiles for the same device share it. Manage Libraries shows assigned profiles and saved/imported context.

Deliberate deviation: import options repeat the verb “Use” to make the sharing action explicit alongside “Keep a separate imported library”; Fluent recommends avoiding repeated option prefixes. The consequence text under the choice explains which data will be kept. Avalonia's existing modal window uses Cancel/Escape/native window dismissal and does not dismiss on outside click, consistent with the application's other forms.

Regression checks cover known-library reuse, explicit reuse of a foreign library, preservation of current saved data and mapping, independent tags and undo history, explicit separate copies and repeated imports, unavailable/incompatible selections, connected-device recommendations, keyboard selection, Escape cancellation, focus restoration and keeping the current profile active. Rendered import dialogs, expanded choices, Config and Manage Libraries were inspected in light and dark themes with 1440×850 and 1000×850 owner windows. These visual checks supplement the interaction tests.

## Saved profile file scan feedback (2026-10-07)

Config and Manage Profiles label the action “Scan profile files”. Visible text explains that it finds saved local profiles by matching settings and favorites files, while Sync library reads device presets. Manage Profiles displays the folder; the button tooltip also identifies the exact filename patterns and folder. These wording and placement choices answer the user's request to explain the operation before starting it.

[Fluent 2 progress-bar guidance](https://fluent2.microsoft.design/components/web/react/core/progressbar/usage) recommends brief labels, meaningful status units, and progress bars for operations longer than one second. [Windows progress-control guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/progress-controls) supports explanatory text and nonmodal indeterminate progress for work of unknown duration. Applied using existing themed Avalonia controls: the button and notification immediately say “Scanning…”, a bar appears after one second if discovery is still running, and completion persists until dismissed with counts of saved, new, and skipped profiles. Fast scans have no artificial delay. File discovery runs on a worker; catalog/settings publication stays on the UI thread. Conflicting profile commands are temporarily disabled; navigation remains available. Errors replace progress with the existing retry notification.

The existing notification supplies a polite accessible announcement, a separate Dismiss button, Escape dismissal, and focus return to the originating scan button. Product choice: use this shared notification for durable completion feedback even when zero new profiles are found. No deliberate deviation from the cited progress guidance. Regression checks cover background responsiveness, discovery and catalog publication, unchanged active profile, repeat scans, failures/retry, keyboard activation/dismissal, and absence of MIDI traffic. Rendered ready, running, and complete states are inspected in light/dark themes at 1000×640 and 1440×850 on both Config and Manage Profiles.

Validation: 196 distinct profile, favorite-editor, compact-layout, storage, and header checks passed across the regression runs, including nine scan-feedback cases. The compact Config scan button retains the existing 32-pixel control height; Manage Profiles retains 28-pixel commands. Real Skia-rendered captures confirmed readable labels, wrapping paths, visible completion feedback, and accessible navigation in both themes and sizes.

The theme selector is temporarily disabled alongside profile commands during discovery because a theme switch rebuilds the visual tree. This preserves the controls and focus origin for the short scan; both theme choices are restored on success or failure. Rebuilding outside a scan clears the scan-command references before registering the new controls.
